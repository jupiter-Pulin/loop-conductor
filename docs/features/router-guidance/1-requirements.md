# 需求交接：自主指导、可持续运行的 Loop Conductor

日期：2026-09-20。交接对象：冷启动的 Claude 实施 agent。

本文描述用户希望得到的行为与交付标准，不规定技术方案、数据 schema、函数签名或文件拆分。收到此交接后，应结合现有代码设计、实施并验证升级；仅补 prompt、调大配置或完成设计文档，不算完成。

## 1. 任务与背景

改造仓库：`/path/to/loop-conductor`。

本仓是 Loop Conductor：内核执行与记录，router 选择下一步，spec/maker/reviewer 执行具体工作，人在 spec 与 merge 处审批，并有显式 help 入口。

用户希望它比普通聊天 agent 更能约束执行风险、保留过程与验收证据，又比固定工作流灵活。router 应成为理解需求、指导 subagent、依据反馈调整计划的负责人。

促成本次改造的真实案例是 `task-20260920-001`，目标仓为 `/path/to/example-target`。其 spec 涉及多链 AMM 网站骨架，包含 38 条 AC、7 个工作包和 10 个待决问题。现有 router 看不到这些内容，也不能把具体指导传给 maker。

交接时该任务停在 `AWAIT_HUMAN(spec)`，尚未批准，原 spec 位于 `specs/task-20260920-001.md`。实施时重新读取状态，不把这个快照当作永久事实。

本次先升级 conductor；升级验收后，用户再批准并运行这个真实任务。不得为演示升级成果而自动批准、启动、合并该任务，或在其目标仓提前实现业务。

## 2. 用户已确定的方向

1. **新增专门的快速摘要 agent。** spec 生成后，由快速模型（例如可用的 Haiku）按固定 prompt 生成带原文引用的摘要，供 router 使用。摘要模型可配置，具体可用模型由实际环境确认。
2. **内核只做摘要的机械校验。** 校验格式、来源版本和引用有效性；不让内核理解、改写或替代模型生成摘要，也不宣称机械校验能证明摘要语义正确。
3. **Router 不得修改 spec，但对如何实现 spec 有自主权。** 拆分、顺序、方法、调查、人员分配、修复方式可以调整；目标、AC、约束和非目标不能由 router 直接或通过 subagent 改掉。
4. **整体运行容量和跨轮持续推进能力必须提升。** 大任务不能依赖一次 agent 会话恰好完成；遇到截断、可恢复故障或运行器重启，应能保留有效工作并继续。
5. **交付可用的升级工作流。** 可分步实施，但最终应能支持真实大任务；不能把一个只读回放、小原型或永久单 maker 限制当成全部交付。

上一轮讨论见 `-1-discovery.md`，它包含曾探索的备选方案。本文确定的需求优先于该探索文档。现有 `AGENTS.md` 与 router-conductor spec 描述旧行为；“router 永不读原文”“只能有四角色”等正是本次拟修改的限制，不能据此拒绝升级。原有安全与审批保证继续保留，除非本文明确改变某项行为。

## 3. 新的目标行为

### R1. 摘要是可回到原文的入口

- 每个需要投入调度的 spec 版本，都有与该版本对应的摘要。新 spec 完成后自动触发生成；已有任务缺摘要时能补齐。
- 摘要让 router 找到任务目标、硬约束、AC 索引、涉及的模块、未决问题，以及原 spec 提议的工作包和依赖。原文中的提议、未知、safe default 不能被改写成已批准事实。
- 每个关键摘要项有可定位到对应版本原文的引用。不存在的文档、无效位置、越界引用或过期版本不能被当成有效引用。
- 人工修订、spec 重写、批准冻结时，要保证 router 最终使用的是当前适用版本的摘要；仅移动文件位置不应造成不可恢复的引用损坏。
- 使用专门、固定且可追溯的摘要 prompt；其职责是压缩与索引，不是批准需求、裁剪范围或制定具有强制效力的实施计划。
- 摘要 agent 只有完成该职责需要的访问与写入能力，不能修改源 spec、产品代码、权限配置或他人的证据。生成过程的成本、失败和模型信息纳入正常案卷与预算。
- 摘要失败、格式错误、引用失效或模型不可用时，应有有界的修复或明确的恢复路径，不能让任务永久卡死。不得静默换成过期摘要、空摘要或由内核猜出的内容；如采用降级路径，应明确可见并仍能访问正确原文。
- 摘要不替代 spec 本身，也不替代人审和 reviewer 的原始验收依据。
- 人审 notes 与后续有效裁决仍作为独立原始依据提供给 router 和执行者，不能因 spec 摘要生成较早而丢失，也不能被摘要覆盖。

### R2. Router 能依据内容做决定

- router 默认读摘要、必要的执行事实和当前任务进展；需要确认时能按引用读取 spec 原文、相关代码、diff 或执行产物。
- 摘要有歧义或与原文冲突时，以适用版本的原文为准；不能要求 router 只能相信摘要。
- router 能识别未知、验证依赖、判断影响范围，并把这些判断转成具体下一步任务。它不必按固定的 spec → 单 maker → review 顺序循环。
- 它能持有可恢复的工作记忆：已确认事实及来源、待验证假设、未决问题、已派工作与当前计划。模型推测与执行事实要可区分。
- 不要求每轮装入完整历史；上下文增长后仍能找到原始记录，不因压缩丢失未完成目标或已批准约束。
- 读取能力不扩大执行权限。Router 不能改 spec，也不能通过委派要求其他 agent 绕开该限制。需要改变产品承诺时，只能提出修订建议并回到人的 spec 裁决。

### R3. Router 可以真正指导多个 subagent

- 每次委派都能向接收者表达本轮目的、输入依据、授权范围、预期产物和完成条件。router 的指导必须实际进入执行上下文，而非只出现在一行路由理由里。
- 允许调查、实验、接口设计、实现、诊断、修复和局部检查等不同任务目的。角色或权限模板的工程设计由实施 agent 决定。
- router 可以调整任务粒度、顺序、依赖与责任人，根据新证据继续、拆分、合并或替换任务，并留下简短理由。
- 同一个产品任务可以有多个有边界的 subagent。无真实依赖且执行边界允许时支持并行；有共享写入或未稳定接口时能串行或协调，不能把并行度当作成功指标。
- worker 在委派范围内自行决定局部实现细节；只有完成、关键阻塞、依赖失效或约束冲突等事件才需要回到 router。避免把每条技术操作都交给中央 router 审批。
- 工作包是可调整的执行计划。Router 可以改变实现路径，但不得借重规划省略原始 AC、扩大产品范围或降低验收要求。
- 子任务退出条件、集成检查与整个产品验收必须分开；研究任务可以不独占某条 AC，一条 AC 也可以由多个任务共同提供证据。
- 支持的子委派都受统一权限、成本、记录和停止控制；递归委派是否开放由实现方案决定，但不能留下不入账、不继承限制的受支持旁路。

### R4. 长任务能跨多轮完成

- 重新审视 router、摘要、spec、maker、reviewer 的 turns、上下文、输出与运行时间容量，以及调度步数、日志长度和整体预算之间的关系。提供适合本案例规模的实际配置与理由。
- 不把“所有上限改成无限”作为解决方案。单次执行与整体任务都保留明确上限；router 只能在用户配置授权的额度内调度。
- agent 达到 turns/context/output 上限时，保留可识别的部分产物、已完成项和未完成项。下轮能据此续做、缩小任务或重新分派，而非默认从头开始。
- 来不及写最终 log 的情况也要可诊断、可恢复：根据可信执行记录与实际残留产物说明已知和未知，不能伪造完成信号或直接把未知视为成功。
- reviewer 对大 diff、多 AC 的检查能够分轮继续。已有检查结果只有在对应版本仍有效时才可沿用，未检查部分必须保持明确，不能为了缩短输出漏掉验收。
- 长摘要、详细诊断和逐条 AC 结果应有完整保存与访问方式。不能为了满足一段短 log 的长度限制而丢失证据，也不能每轮无限重放全部案卷。
- 在运行器持续工作的情况下，只要仍有可执行工作且未触及授权预算、人闸或必须暂停的条件，就应继续推进。提供明确的持续运行方式；单次调度批次耗尽可以让出执行机会，但不能要求用户反复手动启动每一批。
- 分批、续会话、换新会话或重启后，预算与已花成本不得因“新的一轮”而归零。持续运行不能通过创建新批次绕过 runBudget 或任务预算。
- 所有新增角色、重试和子委派都计入同一任务成本。异常中断导致成本未知时明确标注并按既有或改进后的保守策略处理，不能把未知费用当作确定免费。

### R5. 故障后可以恢复，恢复不会重复制造副作用

- 在派工前后、执行中、产物落盘后、提交或集成前后、状态更新前后发生中断，重启后都应能够判断哪些操作已发生、哪些未完成、哪些需要核对。
- 恢复依据来自持久记录和实际执行/产物状态，不依赖上一段对话仍在内存中。不得覆盖旧轮次案卷、丢失待办或重复计算已确认成本。
- 对仍存活的 agent、残留子进程、旧锁和已退出任务作出正确处理，避免因父进程重启就同时跑两个相互冲突的执行者。不能把活锁误当残锁删除。
- 对暂态工具/进程故障、格式错误等可恢复情况，能在有限次数和预算内修复或续推；配置错误、模型不存在等确定性失败应准确报告，避免盲重试。
- 区分慢而有进展、无响应、反复无进展与某个局部能力被阻塞。可恢复的单轮失败不应直接丢弃整个任务；局部失败应尽可能让无关工作继续。
- 有进展的大任务不应仅因轮数多就被无进展保险丝误杀；重复相同工作、换任务名字或改写摘要也不能无限绕过停止机制。
- 过期任务晚到的结果可以保留用于诊断，但不得直接并入新计划或替代当前版本验收。
- 真正耗尽预算、平台限额、人工暂停/放弃、需要产品裁决等情况必须停得清楚，保留恢复材料。默认保留既有预算与限额恢复边界，不擅自增加自动购买、提额或绕过限额行为。
- 整个运行器退出后，至少提供明确且验证过的重启恢复入口；不要求用一个永不退出的进程掩盖恢复缺失。

### R6. 工程边界和最终验收继续成立

- 内核负责执行授权、实际资源上限、可信记录、版本有效性和放行条件；router 负责语义判断与调度。新增摘要不把自然语言理解搬进内核。
- 新增能力必须有可执行的文件、网络、进程与写入边界，并明确哪些由宿主运行时保证。不能仅凭 prompt 或 git 命令文本护栏宣称任意执行已隔离。
- 静态读取、临时实验和产品代码修改的权限按真实副作用区分。安装依赖、运行测试或 codegen 不是天然只读；实验产物不自动并入产品。
- 单个 worker 不得替换获批 spec、修改内核策略、伪造其他角色记录，或把自己的“完成”自述变成最终验收结论。
- 继续区分 agent 自述、执行器事实和独立验收判断。命令成功退出不等于 AC 必然满足；关键验证不能完全依赖同一个 maker 对自己产物的解释。
- 最终仍对整体变更及全部获批 AC 做独立 review，并执行适用的 precommit 检查。局部检查或子任务完成不能取代整体门。
- 保留当前 HEAD/base 对应的 review/precommit 版本约束和批准时复核。需求/输入/计划变化后，相关旧证据不能被错用。
- spec 审批与最终 merge 审批保留，不新增逐次派工或常规重规划的人审要求。真正需要人决定的产品变化仍交人处理。保留不自动 push 的项目约束。

### R7. 用户能看懂当前进度和停止原因

- CLI、案卷和看板能说明：当前目标、活动 subagent、完成了什么、还剩什么、卡在哪里、最近为什么调整计划、花费与剩余额度。
- 明确区分运行中、等待结果、可恢复中断、等待资源、等待人和已终止，不能只留一个长期不变化的“运行中”。
- 每个停止点有具体原因、保留的产物与后续恢复入口。用户无需手工翻 JSON 才知道是否还能继续。
- 新增摘要角色及其状态、版本、原文引用、成本和失败也可追踪；可以查看摘要与原文。
- 记录不需要暴露模型内部思维过程，保留简短决策理由、证据和实际动作即可。

### R8. 能安全接上已有任务

- 新工作流支持新任务，也必须考虑当前这份已经产出 spec、尚待人审的任务；不能要求用户删除任务、重新编号、丢弃案卷或重写需求才能用。
- 保留简单任务直接按 brief 实现的能力，不要求所有小任务都先产出大 spec、摘要和多份委派。是否需要这些步骤由任务内容和现有授权决定，最终安全门仍成立。
- 缺少新摘要或调度数据时有明确补齐路径。既有任务状态、原 spec、人工裁决、成本与产物要保留。
- 人在升级期间修订或批准了 spec，也必须使用与最终获批内容一致的摘要与实施依据。
- 旧案卷仍可读；原本已被标记为只读的遗留任务，不因这次升级意外恢复执行资格。
- 兼容与恢复行为先用隔离副本/夹具验证。真实 `task-20260920-001` 留给用户在升级交付后批准并运行。

## 4. 必须演示的验收场景

以下是行为验收要求，不限定测试组织、内部阶段或协议字段。模拟用于验证故障与调度边界；还需要受控的真实执行来检查实际 CLI、权限与工具行为。

| 场景 | 应观察到的结果 |
| --- | --- |
| 大 spec 正常生成摘要 | 快速摘要 agent 使用固定 prompt 生成当前版本的可引用摘要；router 可回原文；内核只做格式/引用校验 |
| 摘要错引用、生成中断、源 spec 被改或移动 | 不使用无效/过期摘要继续决策；能有限修复或明确恢复，源 spec 不被摘要角色改写 |
| 依赖假设被新证据推翻 | router 修改具体委派或顺序，接收者实际收到新任务；不修改产品承诺，无关工作继续 |
| 多 subagent 协作 | 至少演示一次边界明确的并行工作和结果汇合；共享资源冲突得到处理，最终仍整体审查 |
| maker 中途达到上限 | 已有有效工作保留，下轮从可确认进度续推；不默认从头做、不假称完成 |
| reviewer 未判完全部 AC | 剩余清单可见且可续审；版本变化时不误用旧判决；不能提前打开 merge 资格 |
| 持续运行超过一个调度批次 | 不靠用户反复手动 run，仍在原授权额度内推进；批次边界不重置成本 |
| runner 在派工/落盘/集成关键边界崩溃后重启 | 恢复后无重复并发执行、无重复集成、无覆盖案卷，已完成与未知操作被正确区分 |
| agent 无响应或连续无进展 | 有限恢复后明确停止并保留材料；慢而有进展的任务不被同样处置 |
| router / worker 尝试越权或使用旧证据 | 执行或放行被工程机制拒绝，不能依靠模型自觉回避 |
| 预算、runBudget、限额或人闸生效 | 新调度、摘要生成、续跑和子委派都不能绕过；停止原因和恢复条件明确 |
| 当前待审任务在隔离副本上升级 | 原 spec、状态与历史保留，补齐摘要后能在正常审批后继续 |

本案例可提供三个内容场景：地址尚未核实、无 DB 的 indexer 构建假设、共享契约稳定后 API 与 fixture UI 是否可并行。它们用于证明“反馈改变下一步”；不得把 spec 中的待决默认值当作已批准的范围变更。

## 6. 实施范围与交付

- 实施 agent 自行选择足够简单的工程方案并完成升级，不需要先向用户索取每个实现细节的批准，也不以额外正式 spec 审批作为开工前置。
- 可以分阶段落地与验证，但最终交付覆盖摘要、具体委派、动态调整、多 subagent、持续运行、故障恢复、兼容及最终安全门。先前探索中的最小原型只是实现顺序参考。
- 检查并保留开始时已有的未提交改动，尤其配置、agent-settings 和相关测试；不要覆盖他人工作或借机清理其他任务状态。
- 使用 Node 24 运行本仓 `npm test`，不要在仓库根裸跑 `node --test`。新增测试应真正验证上述行为和故障边界；旧测试中有意被新需求取代的断言可更新，但不能删掉原有安全保证来获得通过。
- 同步当前行为相关的 prompts、配置说明、CLI/看板、`AGENTS.md` 索引和必要测试。对仍未实现的能力明确标注，避免留下多个相互竞争的事实源。
- 交付代码、验证结果、角色和运行额度的配置说明、恢复使用方式，以及 `task-20260920-001` 在用户正常批准后的接续操作说明。
- 测试前后，真实任务的 spec、人闸裁决与目标仓不应被演练修改。受控真实执行使用专门测试任务或临时目标仓，并明确成本；不擅自提高用户现有总预算。
- 完成报告说明：哪些保证由程序强制、哪些仍依赖模型判断；哪些故障场景已实际验证；还有哪些已知限制。不以一次正常流程通过宣称任意中断都可恢复。
