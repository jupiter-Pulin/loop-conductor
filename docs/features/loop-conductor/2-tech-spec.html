Loop Conductor — Agent Loop 最小框架

Feature loop-conductor Owner @pulin Updated 2026-06-11 Approved

1. Requirement Summary

ProblemAgent loop 蓝图（maker 内环 review → verifier 冷验收 → 1/2/3 重试阶梯 → 人类闸门）已在设计讨论中敲定，但仍是伪代码。需要一个可跑的最小系统框架，把状态机、调度、agent 交接全部落地。
Goals① 文件状态机为唯一事实源（state/queue/*.md，人类本地可读可改）；② conductor 为确定性、可重入、幂等的脚本——非 agent；③ bugfix 档全链路手动触发可跑通（最小验收路径）；④ feature 档含本地 spec 审批闸门；⑤ agent 全部 headless spawn，互相只传案卷（dossier）不对话。
Non-Goals不做 dashboard / 可视化；不做 GitHub、webhook 集成（接口预留）；不做 triage-agent（demo 阶段任务由 conductor new 人工创建）；不展开各 agent 内部 prompt / plugin 体系（仅占位文件，后续按 plugin 级单独做 harness engineering）。

项目从零开始，实现骨架已按本 spec 落地：conductor/（状态机 + lib + stages）、tests/（单测 + fake-claude 整合测试）、target/（demo 目标仓库）、agents/（prompt 占位）。无历史包袱。本节列依赖的外部能力：

3. Technical Solution

3.1 Architecture

选型：Node 纯标准库（零 npm 依赖），而非 bash+jq。理由：① claude CLI 输出是 JSON，Node 原生解析，bash 需引入 jq 且错误处理脆弱；② 状态文件 frontmatter 的读写、stage handler 的幂等判断是结构化逻辑，Node 可拆成纯函数做单元测试；③ 零依赖下 Node 与 bash 的部署成本相同。bash 仅存在于 git/claude 的子进程调用里。

状态机全貌。两个人类闸门（spec 审批、最终 merge）都是异步状态转移，conductor 读到状态变化才推进，绝不阻塞等待：

stateDiagram-v2 [*] --> NEEDS_SPEC : feature 档 [*] --> READY : bugfix 档 NEEDS_SPEC --> AWAIT_SPEC_APPROVAL : plan-agent 产出 spec 草稿 AWAIT_SPEC_APPROVAL --> READY : approve → 冻结 spec AWAIT_SPEC_APPROVAL --> NEEDS_SPEC : reject + notes READY --> VERIFY : maker 完成 且 green gate 过 READY --> FAILED_BOX : green gate 不过 VERIFY --> AWAIT_HUMAN_MERGE : verdict pass（终点） VERIFY --> FIXING : verdict fail 且 miss < 3 VERIFY --> FAILED_BOX : miss ≥ 3 FIXING --> VERIFY : 修复后 green gate 过 FIXING --> FAILED_BOX : green gate 不过 / 预算超限 AWAIT_HUMAN_MERGE --> [*] : conductor merge 归档 FAILED_BOX --> READY : conductor retry（人工）

3.2 Data Model

目录结构（worktrees/、state/.lock 进 .gitignore）：

will-workflow/
├── conductor/               # conductor.mjs（CLI 入口+drain）、lib/（state claude lock git）
│                            # stages/（每 stage 一个 handler，签名 (task, cfg) => void）
├── conductor.config.json    # target 路径、testCommand、budgetUsd、maxTurns、各角色 model
├── agents/                  # plan / maker / verifier 的 prompt 占位
├── state/                   # queue/（活跃，唯一事实源）done/（归档）failed/（收件箱）.lock
├── specs/                   # feature 档 spec 草稿（审批后冻结副本进 dossier）
├── dossier/<id>/            # 案卷（见下表）
├── worktrees/<id>/          # target 的任务隔离检出，跨轮持久（gitignore）
└── target/                  # demo 目标仓库（独立 git repo，预埋 bug）

任务文件 = YAML frontmatter（机器读）+ Markdown 正文（人读）。bugfix 档的 spec 就是正文里的「验收标准」段：

---
id: task-20260611-001
kind: bugfix                # bugfix | feature
stage: READY                # 状态机驱动；全部字段为扁平标量，自写极简解析器
miss_count: 0
maker_session_id: null      # miss==1 时 claude -r 用
spent_usd: 0                # 预算闸：累加各 spawn JSON 的 total_cost_usd
approval: null              # 审批闸门：approved | rejected
---
正文（人读）：## 标题与证据；## 验收标准（bugfix 档此段即 spec，READY 时抽取为 dossier/spec.md）；## reject_notes（reject 时追加喂回 plan-agent）

案卷 dossier/<id>/ 是 agent 间唯一通信媒介，verifier 永远只读 spec.md，不感知档位差异：

文件写入者用途
spec.mdconductor（冻结时复制）verifier 与 maker 的契约面
<role>-r<n>.jsonconductorspawn 记录：原始 CLI JSON（session_id、cost）+ started/done 双标记，所有角色统一留档
review-findings.mdmaker 内嵌 reviewer（hook 落盘）内环 review 原始记录，不经 maker 转述
verify-r<n>.md / verify-r<n>.verdict.jsonconductor（解析 verifier 终输出后落盘）叙事 + 机器可读裁决 {"verdict":"pass|fail","reasons":[]}；轮次 n = miss_count + 1（首验 r1）
timeline.mdconductor 追加事件日志，人类排查用

3.3 CLI Interface

命令作用
conductor run一次 drain：循环推进所有任务直到无状态变化（全局步数上限 20/次 run；耗尽记日志，下次 run 续推）。cron / GH Actions 的唯一入口
conductor new --kind bugfix|feature --title "…"从模板生成任务文件（bugfix 初始 READY，feature 初始 NEEDS_SPEC）
conductor approve|reject <id> [--notes "…"]人类闸门：写 approval 字段 + reject_notes。仅是状态文件的安全包装，手编文件等效
conductor status打印任务表（id / kind / stage / miss / spent）
conductor merge <id>终点闸门：人在 worktree 看完 diff 后执行 → merge 分支、归档至 done/、清 worktree
conductor retry <id>FAILED_BOX → READY，重置 miss，保留案卷

claude CLI 调用约定（封装在 lib/claude.mjs 单点）：

角色调用关键约束
planclaude -p … -C target/ --tools Read,Grep,Glob --output-format json工具集硬限制只读；spec 草稿从 JSON result 捕获、由 conductor 写入 specs/<id>.md——只读 agent 自身不落盘
maker 首轮claude -p … -C worktrees/<id> --output-format json--permission-mode acceptEdits；session_id 落盘 frontmatter
maker 续（miss==1）claude -r $session_id -p "findings 见 dossier/verify-r1.md" --output-format jsonresume 失败则自动降级为冷启动路径
maker 冷（miss==2）claude -p …(spec+全部案卷) -C worktrees/<id> --output-format json全新 session，赌冷启动红利
verifierclaude -p … -C worktrees/<id> --tools "Read,Grep,Glob,Bash(git diff:*),Bash(git log:*)" --output-format json工具集硬限制只读，不跑测试——行为验证由 green gate 承担，静态不够再放开；不读 maker 叙事；verdict JSON 从终输出捕获、conductor 落盘并只认该文件

3.4 Core Logic

Stage handler 一览（每个 handler 必须先查「动作是否已发生」再行动）：

Stage动作 → 转移幂等保证
NEEDS_SPECspawn plan-agent（带 reject_notes）→ conductor 写 specs/<id>.md、重置 approval=null → AWAIT_SPEC_APPROVALspec 草稿已存在 → 不重 spawn，直接转 AWAIT_SPEC_APPROVAL（崩溃恢复）
AWAIT_SPEC_APPROVALapproved → 复制 spec 进 dossier（冻结）→ READY；rejected → 收 notes 进任务正文、归档旧草稿 → NEEDS_SPEC；否则不动纯读字段，天然幂等；归档旧草稿保证 NEEDS_SPEC 的「草稿已存在」检查不误判
READYensure_worktree → spawn maker → conductor 亲自跑 testCommand（green gate）→ 绿 VERIFY / 不绿 FAILED_BOX双标记：有 started 无 done → 判定上次崩溃，转 FAILED_BOX（原因=crashed），人工 retry 恢复——不留滞留任务
VERIFYattempt = miss+1；spawn verifier → conductor 落盘 verify-r<attempt>.verdict.json → pass AWAIT_HUMAN_MERGE / fail 则 miss++，<3 进 FIXING，≥3 进 FAILED_BOXverify-r<attempt>.verdict.json 已存在 → 直接消费不重验
FIXINGmiss==1 resume 原 maker / miss==2 冷 maker → green gate → VERIFY同 READY 双标记（轮次号入文件名）；崩溃同样转 FAILED_BOX
AWAIT_HUMAN_MERGE / FAILED_BOX终态，只响应人工 merge / retry 命令—

四条全局机制：

  1. 先产物后状态：所有 handler 先把产物落盘（spec、verdict、案卷），最后一步才改 frontmatter 的 stage。崩溃最坏导致重复读产物，不会丢转移。
  2. 并发锁：mkdir state/.lock（POSIX 原子）+ 内写 pid/时间戳；mtime 超 30 分钟打印 stale 告警，demo 阶段人工删除。
  3. green gate 不信口供：maker 说什么不算，conductor 在 worktree 里亲自跑 cfg.testCommand，只认 exit code。
  4. 预算闸：每次 spawn 带 --max-turns；JSON 输出的 total_cost_usd 累加进 spent_usd，超 cfg.budgetUsd（默认 5）拒绝再 spawn、直接 FAILED_BOX。

Worktree 生命周期：READY 进入时 git -C target worktree add ../worktrees/<id> -b task/<id>；FIXING/VERIFY 各轮复用同一检出（代码状态即 maker 的外部记忆）；仅 merge 或人工归档时移除。

3.5 UI/UX Contract

N/A——无前端界面。人机接口就是状态文件与 CLI 本身：审批 = conductor approve task-xxx（或直接手编 frontmatter，文件是唯一事实源）；review 终稿 = 在 worktrees/<id> 里 git diff main...task/<id> + 读案卷。Dashboard / GitHub PR 集成是后续在状态文件之上加的投影层，不改本框架。

4. Risks & Dependencies

RiskSeverityMitigation
token 花费失控（agent 自循环、重试阶梯叠加）High三层闸：per-spawn --max-turns、per-task spent_usd 预算、重试阶梯硬上限 3。全部由 conductor 代码强制，不依赖 agent 自觉
claude CLI JSON schema / flag 漂移Medium调用收敛在 lib/claude.mjs 单点；fake-claude stub 测试不依赖真 CLI（见 §6）
maker 谎报完成 / 改绿了别的测试Mediumgreen gate 由 conductor 跑全量测试；verifier 冷上下文静态对照 spec
conductor 崩溃留 stale 标记 / 残锁Mediumstarted/done 双标记 + 锁 mtime 检测；demo 阶段人工 retry 兜底，不做自动恢复
claude -r 会话过期或不可恢复Lowresume 失败自动降级为 miss==2 的冷启动路径，阶梯顺延

6. Testing Strategy

LayerCoverage
Unitstate.mjs frontmatter 解析/序列化往返；stage handler 纯函数化后的转移逻辑（每个 stage × 每个分支）；锁的获取/stale 判定
Integrationfake-claude stub（PATH 前置的假二进制，按调用序返回脚本化 JSON）驱动 conductor 全状态机：正常路径、verdict fail×3、崩溃重入、预算超限、并发双开——全程零 token
E2E（最小验收路径）真 claude 跑 bugfix 档：target/ 预埋 bug → new --kind bugfix → run → 经 READY/VERIFY 到 AWAIT_HUMAN_MERGE → 人在 worktree 验 diff → merge。通过标准：bug 修复、测试绿、案卷完整、归档正确
fake-claude stub 是本项目的测试支点：状态机的全部分支（包括崩溃和重试）都必须能在不花一分钱的情况下回归。真 claude 只出现在 E2E。
